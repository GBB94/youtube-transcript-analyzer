[2] ZACH: What would an eval harness look like?
--------------------------------------------------------------------------------
CLAUDE (summary): Four pieces — a golden set (20-50 hand-labeled examples), a runner
(push each example through the pipeline), scoring functions (per-field metrics), and
a diff (run A vs run B). Grounded to the Fireflies dashboard:
  - Golden set: hand-label correct extractions (competitors, persona, buying signals).
    Start with 20. The labels are ground truth.
  - Runner: loop feeding each transcript through the current prompt; swappable.
  - Scoring: competitor mentions = precision/recall (a hallucinated competitor is
    worse than a missed one); persona = classification accuracy; free-text summaries
    = LLM-as-judge faithfulness score.
  - Diff: per-metric A/B table. Prompt changes become measured, not vibes.
The mental shift: you're building a ruler. Offered to scaffold it.

[3] ZACH: How hard would it be to build a repository of YouTube video transcripts
    I could query? e.g. the Moonshot podcast, last two years via YouTube — easy /
    possible? Or is there a better way?
--------------------------------------------------------------------------------
CLAUDE (summary): Very doable — a classic RAG project, roughly a weekend build.
Difficulty is lopsided: retrieval architecture is easy/stable; the transcript
extraction layer is the fragile part.
  - Extraction gotcha: youtube-transcript-api works from a laptop but YouTube blocks
    most cloud/datacenter IPs (IpBlocked). Rule: run ingestion locally. Managed APIs
    (~$5/mo) handle IP rotation but you don't need them for a one-time backfill.
  - Pipeline (textbook RAG): (1) enumerate channel videos via YouTube Data API v3;
    (2) pull each transcript locally; (3) chunk and KEEP TIMESTAMPS (enables "at
    34:12 in EP X" deep links — the feature that makes it feel magic); (4) embed +
    store locally (Chroma/LanceDB — no hosted vector DB needed at this scale);
    (5) query: embed question, pull top chunks, hand to Claude with citations.
  - "Better way" fork: auto-captions don't tell you who said what. Higher-fidelity
    path = pull audio with yt-dlp + Whisper + diarization (pyannote) for speaker
    labels. Recommendation: start with captions end-to-end, upgrade later if speaker
    attribution matters. Retrieval half doesn't change.
Offered to scaffold the captions version.

[6] ZACH: Yes, pull the last two years — but first, where will you store these and

CLAUDE (summary): Proposed the canonical-vs-derived principle: pull once (the slow,
rate-limited, occasionally-blocked step), treat as source of truth, never discard;
everything else rebuilds from it. Three layers:
  1. Canonical raw JSON per episode (segment-level timestamps + metadata) — source
     of truth. (The 45s Markdown is lossy; keep raw segments to re-chunk freely.)
  2. Readable Markdown per episode (deep-linked) — derived.
  3. Query index (chunk -> embed -> local vector store with video_id + start_sec on
     every chunk) — derived, rebuildable.
Plus manifest.json for incremental (only-new) ingest. Sequencing: pull + store
canonical first, then build the index. (A multiple-choice question about embeddings,
scope, and storage location was attempted but didn't render for the user.)

[7] ZACH: First — is there a better/more efficient way to pull these worth the
    effort? How do we engineer this so querying stays efficient/manageable when the
    text is very large? Let's research best practices.
--------------------------------------------------------------------------------
CLAUDE (researched + synthesized):

  1) Pulling efficiently — at this scale, no heroic infra needed.
     - ~100 episodes is small; the bottleneck is YouTube's soft rate limit
       (~100-200 req/hr/IP) and intermittent blocks, not compute.
     - Counterintuitive best practice: pull SEQUENTIALLY and slowly from one IP.
       Parallelism gets you throttled. --sleep-interval 5 --max-sleep-interval 15;
       a 600-video channel ~40 min, so ~100 is well under.
     - Efficiency win: one yt-dlp pass with --write-info-json --write-subs
       --skip-download grabs captions + metadata + CHAPTER MARKERS together
       (chapters = free semantic chunk boundaries).
     - The official captions.download API is owner-only — useless for third-party.
     - Real "better way" fork = quality (captions vs audio+Whisper+diarization for
       speaker labels), not speed. Recommend banking captions now, upgrading later.

  2) Staying manageable at scale — the core principle is reassuring.
     - You NEVER send the corpus to the model. RAG decouples query cost from corpus
       size: a query retrieves a fixed handful of chunks whether 100 or 10,000
       episodes. Tokens-to-LLM stay flat.
     - What degrades with scale is retrieval PRECISION. The stack that holds it up:
        a. Two-stage retrieval: wide cheap net (hybrid dense + BM25, top ~50-100)
           then rerank with a cross-encoder to top 5-10. (Hybrid + rerank cut
           Anthropic's retrieval failures ~67%.)
        b. Hybrid search, not pure vector — BM25 nails proper nouns/jargon that
           dense vectors fuzz ("Gemini 3", "Kush Bavaria", "po-token").
        c. Contextual Retrieval (Anthropic): prepend a 50-100 token LLM-generated
           context blurb to each chunk before embedding (fixes floating pronouns in
           conversation). Cut retrieval failures ~49% alone. Prompt-cache the episode
           body to control cost. Highest-leverage ingest move here.
        d. Metadata filtering: every chunk carries {video_id, upload_date,
           start_sec, end_sec} — enables time-scoped queries and deep links.
     - Chunking consensus for transcripts: 300-600 tokens, ~10-15% overlap, break on
       natural boundaries (utterance ends, chapter marks). Never flatten timestamps.
     - Vector store: LanceDB (single memory-mapped file, no server, scales to
       millions) preferred over Chroma for future-proofing.

  3) Best-practice architecture end to end:
     - Ingest once: pull captions+metadata -> store raw JSON (canonical) -> chunk ->
       contextualize -> embed -> store in vector DB + BM25 index.
     - Query: hybrid retrieve ~50-100 -> rerank -> ~8 -> Claude answers with
       citations to episode + timestamp deep link.
     - Evaluate: small golden Q&A set so chunking/embedding changes are measured.

  Decisions flagged: (a) speaker labels — captions now or diarize first;
  (b) contextual retrieval on by default?; (c) embeddings local vs API.

[9] ZACH: What's still open? Ask it here.  ->  (answered the multiple-choice)

Three decisions surfaced:
  - Contextual enrichment on by default?  -> ZACH: On by default.
  - Embeddings local vs API?              -> ZACH: Local model.
  - Speaker attribution — when?           -> ZACH: "how important is this when
    searching through the transcripts?"

CLAUDE (on importance of speaker labels): Least load-bearing of the three for a
query system. Most searches (topic/factual) are unaffected by who spoke. It matters
only for a slice: attribution queries ("what did the guest argue"), multi-voice
debates where positions differ, and clean quote attribution. Softeners: YouTube
auto-captions already include >> turn-change markers (rough boundaries, no names),
and diarization is the one upgrade that's cheap to add later (speaker field reserved;
retrieval layer unchanged). Cost of doing it now: R0 becomes audio->Whisper->
diarization->alignment (hours, heavier deps). Recommendation: captions now, diarize
later, unless speaker-attributed analysis is a primary use case.
